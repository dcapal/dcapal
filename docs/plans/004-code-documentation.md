## Context and Orientation

The repository root is a pnpm workspace with a Rust backend and a React frontend. The backend's inbound REST adapter is under `dcapal-backend/src/ports/inbound/rest`; its domain entities are under `dcapal-backend/src/app/domain/entity.rs`. The frontend application and its browser-test helpers are under `dcapal-frontend/src` and `dcapal-frontend/tests`. The typed API package is under `packages/api-client`; `src/mutator` is hand-written, while `src/gen` and `src/gen-mocks` are produced from `dcapal-backend/docs/openapi.json` by `orval.config.ts`.

The documentation scope is the code added or materially changed by `master...HEAD`, excluding data files, lockfiles, workflow/config-only changes, deleted files, and generated Orval output. Deleted legacy files have no remaining API surface to document. Modified JavaScript files remain in scope because they are changed application modules and expose public components or constants.

## Plan of Work

First build an inventory of changed hand-written source files and public symbols. Check each public export for an existing useful comment before adding one. Group comments by responsibility: API-client configuration and errors, frontend data hooks and components, test fixtures/journeys, backend domain types, REST request/response models, and OpenAPI helpers.

Describe purpose, inputs/outputs where those are not clear from the signature, and important wire or lifecycle guarantees. Do not narrate the implementation line by line. Add private comments only for reasons such as preserving decimal precision, preventing duplicate authentication headers, inlining local JSON schema references for OpenAPI consumers, or keeping test coverage collection aligned with the browser process.

For the generated client, add or improve stable documentation in `packages/api-client/README.md`, `packages/api-client/orval.config.ts`, and `packages/api-client/src/index.ts`. Keep generated files unchanged except for regeneration if the source specification or generator requires it. If the OpenAPI schema needs a description for a public wire model, update the Rust source that owns the schema or the checked-in OpenAPI source rather than hand-editing generated TypeScript.

Finally run the repository's format, typecheck, unit, backend, API-client, and browser checks. Review the diff for comments that merely repeat names or code mechanics, and confirm unrelated user files remain unstaged.
